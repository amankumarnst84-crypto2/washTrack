# WashTrack backend

Updated 18 November 2026. JavaScript, Node.js, Express 5, CommonJS, PostgreSQL and Prisma Client 6.19.0.

## Start

From this server directory:

```sh
npm ci
cp .env.example .env
# Edit your DATABASE_URL, JWT_SECRET and DEMO_PASSWORD locally.
npm run db:generate
npm run db:migrate
npm run db:seed
npm start
```

For the existing configured laptop, keep its `.env` and skip copying the example. Default API: http://127.0.0.1:3001. PostgreSQL must be running. In the complete project, root `npm i` installs both dependency sets and root `npm run dev` prepares the database and launches both servers together. Do not start a separate API process when using that command. Vite proxies `/api` to the backend. If `../dist/index.html` exists, the backend also serves that frontend build.

The seed creates fictional student and staff accounts using the password you put in DEMO_PASSWORD. It does not reset existing passwords or orders. Account emails: student@washtrack.test, student2@washtrack.test, staff@washtrack.test.

## What is complete

- Student registration using name, email, assigned bag number and password.
- Login, current user, role-based authorization and logout that invalidates old JWTs.
- Clothing type/quantity entry, 1–15 total, one active bag/order, persisted PostgreSQL records.
- Ownership-protected order lists, individual order details and status history.
- Optional API search (`q`) and status filters. No pagination yet.
- Received confirmation, morning/evening lots, lot-wide washing, individual counter-ready confirmation and staff handover.
- Delay reasons, missing/extra/quality complaints, staff response history and student-only final resolution.
- Transactions, uniqueness/CHECK constraints and validation/error responses.

## Student signup workflow

1. Student submits name, email, bagNo, password and confirmPassword to `POST /api/auth/register`.
2. Backend validates the input and creates a STUDENT account with a bcrypt password hash.
3. Student signs in. Registration does not create a login cookie.

Email and bag must be unique. Public STAFF registration is rejected. Use B-69 / G-76 format. Passwords require 8 characters minimum and 72 UTF-8 bytes maximum.

Invitation codes and their API have been removed. The legacy RegistrationInvite table and migrations are retained so existing data is not dropped. They are not used by signup.

For a new setup, set JWT_SECRET in server/.env to a random value of at least 32 characters from your password manager. Keep it private; an existing secret does not need changing.

## Authentication

JWT cookie: washtrack_session, HttpOnly, SameSite=Strict, eight-hour lifetime. Secure flag is enabled in production. The database determines role and bag ownership. Role selector/URL/body values do not grant staff access.

User.tokenVersion is stored in each JWT. Logout increments the database version, making all previously issued tokens for that account invalid, including copied cookies. Other devices must sign in again. The new migration also requires users with old-format cookies to sign in again.

Login allows 30 attempts per IP per 15 minutes; registration allows 20. These in-memory limits are suitable for the single-process academic demo. Separate-origin frontend hosting is not enabled: use the included Vite same-origin proxy or combined hosting. Writes require a JSON object and matching Origin when supplied.

## Database and migrations

Use the committed migrations, never a shared-database reset. The new `202611180001_registration` migration adds User.tokenVersion and RegistrationInvite without dropping or rewriting existing accounts/orders.

There are now eight models: User, Order, OrderItem, OrderEvent, Lot, Complaint, ComplaintEvent, RegistrationInvite. The teammate's five manually created tables have not been mapped to this schema. Their schema-only SQL is still needed. Do not apply these initial migrations to that existing database without first agreeing a mapping/baseline. The verified local demo uses its separate washtrack_demo_20261111 database.

IDs are full UUIDs generated by Prisma and protected by primary-key constraints. Existing frontend abbreviated WT labels are only display labels and are not guaranteed unique; all API paths use the full UUID. No sequential order-number field is introduced.

## Code guide

- src/index.js: environment, startup, database connection, static frontend and graceful shutdown.
- src/app.js: middleware and laundry REST routes, plus route-level transactions.
- src/registration.js: public student signup.
- src/auth.js: JWT validation, database identity and role guard.
- src/rate-limit.js: reusable per-IP request limiter.
- src/db.js: one shared Prisma Client.
- src/rules.js: item types, counts and validation helpers.
- prisma/schema.prisma: data model and relations.
- prisma/migrations/: append-only SQL migration history.

Prisma CLI transitive dependency overrides and existing package versions remain unchanged. Registration uses existing bcryptjs for password hashing. Application code does not import Node crypto directly; authentication libraries still perform cryptographic operations internally.

## Outside current scope

Payments, paid services, garment photos, automatic machine tracking, cancellation, ETA prediction, public staff signup, password reset/email verification, bag-reassignment administration and SMS/push notifications are not implemented. Existing frontend polls the API every ten seconds. The exact classroom authentication example still has not been supplied for comparison.
